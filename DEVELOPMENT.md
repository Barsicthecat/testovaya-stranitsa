## Ошибка 1. Кириллица в имени репозитория

- **Симптом:** при создании репозитория с именем «Тестовая страница» через GitHub API
  ответ вернул `201 Created`, но репозиторий назывался `-`, а не задуманным именем.
- **Причина:** GitHub допускает в имени репозитория только латиницу, цифры, `-`, `_` и `.`.
  Незнакомые символы он молча отбрасывает — из «Тестовая страница» остался один дефис
  (из пробела). Никакой ошибки при этом не возвращается.
- **Исправление:** имя репозитория — транслитерация `testovaya-stranitsa`,
  русское название вынесено в поле «описание» репозитория (отображается на GitHub
  под именем).
- **Проверка:** `GET /repos/Barsicthecat/testovaya-stranitsa` → `200`, описание
  «Тестовая страница» на месте.

## Ошибка 2. Китайские иероглифы в демо-данных

- **Симптом:** при вычитке сгенерированных демо-данных в описании проекта
  «Печкин Телеграф» обнаружились иероглифы «写信» вместо части русского текста.
- **Причина:** артефакт генерации текста (модель «съехала» на другой язык
  посреди строки).
- **Исправление:** текст переписан полностью на русском.
- **Урок:** после генерации контента всегда вычитывать его целиком.

## Ошибка 3. Страница «мертвая»: 0 проектов, пустая статистика

- **Симптом:** на эмуляторе страница открылась (шапка, поиск — на месте),
  но статистика «0 всего • 0 в работе • 0 завершено», карточек нет,
  и даже пустое состояние не показывалось. Скрипт явно падал до `render()`.
- **Диагностика:** добавлен видимый аварийный перехватчик ошибок
  (`window.addEventListener("error", …)` — выводит красный баннер внизу экрана,
  т.к. консоли на мобильном экране нет). Но баннер не появлялся, потому что
  Chrome отдавал `app.js` из кеша (см. ошибку 4).
- **Причина:** `crypto.randomUUID()` доступен **только в безопасном контексте**
  (HTTPS или localhost). Страница открывалась по `http://10.0.2.2:8765` —
  это не безопасный контекст, метод `undefined` → `TypeError` при первом же
  вызове `seedProjects()` → скрипт умирает до выполнения `render()`.
- **Исправление:** написана своя функция `uid()`:
  ```js
  function uid() {
    if (crypto.randomUUID) return crypto.randomUUID();
    const b = crypto.getRandomValues(new Uint8Array(16));
    // … выставление бит версии RFC 4122, hex-строка
  }
  ```
  `crypto.getRandomValues()` работает и в небезопасном контексте.
  Все 11 вызовов `crypto.randomUUID()` заменены на `uid()`.
- **Проверка:** перезагрузка страницы → статистика «10 • 6 • 2», карточки
  рендерятся (uiautomator + скриншот + vision-анализ).

## Ошибка 4. Кеш Chrome: правки не применяются

- **Симптом:** после исправления ошибки 3 и перезагрузки страницы
  (`KEYCODE_REFRESH`) страница вела себя как старая (0/0/0), а лог
  `python -m http.server` показывал: новых запросов нет вообще.
- **Причина:** Chrome на эмуляторе агрессивно кеширует статику; refresh
  не доходит до сервера — всё отдается из кеша. `python -m http.server`
  не отправляет `Cache-Control: no-store`.
- **Исправление (двухчастное):**
  1. версионирование ассетов в `index.html`: `styles.css?v=2`, `app.js?v=2` —
     при следующем изменении bump до `?v=3`;
  2. для тестов — открытие страницы с уникальным параметром:
     `http://10.0.2.2:8765/?fresh=N` (N увеличивается).
- **Урок:** при loop-тестировании на эмуляторе всегда либо версионировать
  ассеты, либо открывать URL с уникальным query-параметром.

## Ошибка 5. `adb input text` не умеет кириллицу

- **Симптом:** попытка ввести «Звёздный Каталог» в поле формы через
  `adb shell input text` падала: `NullPointerException` внутри
  `InputShellCommand.sendText`.
- **Причина:** известное ограничение Android — `input text` не поддерживает
  non-ASCII символы (кириллицу, эмодзи и т.п.). Клавиатура на headless-эмуляторе
  также недоступна для программного ввода.
- **Исправление:** ввод выполнен через **Chrome DevTools Protocol (CDP)**.
  На эмуляторе у Chrome есть сокет `chrome_devtools_remote`; проброшен через
  `adb forward tcp:9222 localabstract:chrome_devtools_remote`, написан
  минимальный WebSocket-клиент на чистых сокетах Python (без зависимостей),
  который выполняет JS в контексте страницы: заполнение полей формы
  `dispatchEvent`-ами и отправка через реальный обработчик `submit`.
- **Проверка:** E2E-сценарий создания проекта «Звёздный Каталог» —
  карточка создана, в `localStorage` 11 записей, тост показан.

## Ошибка 6 (методологическая). Неверный тест ширины 320px

- **Симптом:** первый тест «узкого экрана» через `wm size 320x640` давал
  скриншот, не соответствующий ожидаемой верстке (гигантские элементы),
  а vision-анализ путался в описании.
- **Причина:** `wm size` меняет физическое разрешение, но не плотность
  (density). У AVD Pixel 6 плотность 420 dpi (~2.625x), поэтому
  320 физических пикселей = ~122 CSS-пикселя — нереально узкий экран,
  который ни одно устройство не имеет.
- **Исправление:** для честных 320 CSS px:
  `wm density 160` + `wm size 320x640`, после теста —
  `wm size reset` + `wm density reset`.
- **Проверка:** числовая проверка через uiautomator (точные bounds элементов):
  заголовок «Проекты» [14,109]→[132,139], кнопка «Новый» [200,102]→[306,146] —
  зазор 68px, перекрытия нет; правый край кнопки 306 < 320; поле поиска
  [51,181]→[260,226] — в пределах экрана.

## Ошибка 7. Сырой CDP-сокет без WebSocket-handshake

- **Симптом:** первая версия CDP-клиента отправляла CDP-фреймы сразу после
  TCP-подключения к `chrome_devtools_remote` — соединение закрывалось
  (`ConnectionError: socket closed`).
- **Причина:** DevTools-сокет говорит по протоколу **WebSocket**; прежде чем
  обмениваться CDP-сообщениями, нужно выполнить HTTP Upgrade-handshake
  (`Upgrade: websocket`, `Sec-WebSocket-Key` …), а затем маскировать
  клиентские фреймы.
- **Исправление:** клиент переписан: полноценный WebSocket-handshake +
  корректные фреймы (маскировка клиентских сообщений, обработка ping/pong,
  склейка фрагментированных фреймов).
- **Проверка:** `1+1` → `RESULT: 2`, затем весь E2E-прогон.

## Ошибка 8 (аудит). Краш страницы на повреждённом localStorage

- **Симптом (найден аудитом с живыми CDP-тестами):** при записи в
  `localStorage` массива мусора (`[1, "строка", null, true]`) страница
  показывала статистику «4 всего» без карточек, а ввод в поиск валил рендер:
  красный баннер `TypeError: Cannot read properties of null (reading 'status')`.
  Пустые объекты `[{}, {"x":1}]` рендерились карточками с заголовком
  «undefined»; `progress: 999` давал «999%» и переполнение дорожки.
- **Причина:** `loadProjects()` проверял только `Array.isArray(data)`, но не
  форму элементов. `renderList` падал на `p.name.toLowerCase()` у не-строк,
  `renderStats` — на `null.status`. Прогресс не был зажат в 0–100.
- **Исправление:** добавлена `sanitizeProject(p)` — нормализация каждого
  элемента при загрузке: не-объекты отбрасываются; `name` — только непустая
  строка (≤60 симв.), иначе элемент отбрасывается; `desc` — строка ≤300 симв.;
  `category`/`status` — только известные ключи (иначе `other`/`idea`);
  `progress` — clamp 0–100; отсутствующий `id` генерируется. Если после
  чистки не осталось ничего, а исходник был непустым мусором — засеиваются
  демо-данные (честный пустой `[]` остаётся пустым списком).
- **Проверка (все сценарии воспроизведены и перезапущены):**
  - `[1,"строка",null,true]` → 10 демо-карточек, поиск работает, баннера нет
  - смесь валидных и мусорных → 5 валидных карточек, «Кламп» 999→100%,
    «Негатив» −50→0%, XSS-имя из LS отображается экранированным текстом
    (`&lt;img…`), выполнение — 0
  - `[]` → пустое состояние «Пока ни одного проекта»
  - regression: создание проекта → reload → персистентность (11 карточек)
- **Формальная верификация:** ad-hoc скрипт `hermes-verify-p1-sanitize.py`
  (CDP, живая страница): сценарии A (мусорный массив, 4 проверки),
  B (смесь валидных+мусор, 6 проверок), C (честный пустой `[]`, 2),
  D (regression создание/reload, 2) — **14/14 PASS**. Коммит `cd9aa75`.

## Ошибка 10 (аудит, П2). Прогресс без clamp при рендере

- **Симптом (найден аудитом):** `renderList()` подставлял
  `Number(p.progress) || 0` напрямую в CSS `width` и label — значения
  вне 0–100 (999, −50) рисовали переполненную дорожку и «999%».
  П1 закрыл вход через `loadProjects`, но данные могли бы попасть в память
  и другим путём (будущая синхронизация вкладок и т.п.).
- **Исправление (П2):** в `renderList()` добавлен clamp при рендере —
  `const prog = Math.min(100, Math.max(0, Number(p.progress) || 0))`,
  `prog` используется и в `width`, и в label. Defense-in-depth: даже
  «плохой» массив в памяти отрисуется корректно.
- **Верификация (ad-hoc, 13/13 PASS):** STATIC (clamp-строка внутри
  `renderList`, сырой прогресс удалён из шаблона — 4 проверки) +
  UNIT (формула в живой странице: 999→100, −50→0, 'abc'→0, 42.7→42.7,
  границы 0/100, null/undefined→0 — 8 проверок) + INTEGRATION
  (LS `progress:999` → DOM `width:100%`, label `100%`).
- **Повторная верификация (stale-gate, 10/10 PASS):** HEAD `e392a41` ==
  чистое рабочее дерево; живая страница на `app.js?v=4`: 10 демо-карточек,
  баннера ошибок нет, «Северный Ветер» с корректными 65%.

## Ошибка 11 (инфраструктура верификации). CDP-таргет «уплывал» на старую вкладку

- **Симптом:** интеграционный тест П2 трижды показывал FAIL при записанном
  LS: `localStorage` содержал «Интеграцию», а DOM — демо-данные.
- **Причина:** `am start` с новым URL открывает в Chrome НОВУЮ вкладку
  (номер CDP-таргета растёт: 8 → 13 → 14), а скрипт продолжал обращаться
  к захардкоженному таргету №8 — старой фоновой вкладке с замороженным
  DOM. LS у вкладок одного origin общий, поэтому запись проходила, а
  чтение DOM шло из «прошлого».
- **Исправление (в проверочном скрипте):** номер таргета ищется
  динамически через `GET /json` по подстроке URL активной вкладки.
- **Урок:** при CDP-тестировании никогда не хардкодить номер таргета —
  всегда резолвить по URL.

## Ошибка 12 (аудит, П3). Фокус не возвращался после закрытия модалки

- **Симптом (найден независимым ревьюером):** `openModal()` перемещал
  фокус в диалог, но `closeModal()` не возвращал его на кнопку-триггер.
  Пользователи клавиатуры и скринридеров после закрытия «терялись» в
  начале страницы — нарушение WCAG 2.4.3 (Focus Order). Вторая часть:
  `<dialog>` не был связан с заголовком (`aria-labelledby`).
- **Исправление (П3):**
  - `let lastFocused` — в `openModal()` сохраняется
    `document.activeElement`;
  - `closeModal()` после `modal.close()` возвращает фокус:
    `if (lastFocused && document.contains(lastFocused)) lastFocused.focus()`
    (проверка `document.contains` — триггер мог быть удалён вместе с
    карточкой);
  - `<dialog aria-labelledby="modal-title">` — скринридер объявляет
    заголовок диалога.
- **Верификация (ad-hoc, 12/12 PASS):** STATIC (сохранение activeElement,
  возврат фокуса, aria-labelledby, ?v=5) + LIVE: фокус уходит в модалку
  (INPUT:f-name); после «Отмена» — на кнопку «Новый»; после Esc
  (cancel-событие) — на кнопку «Изменить» той же карточки; после
  «Сохранить» — на кнопку «Новый»; regression: карточки на месте,
  создание/удаление работает.
- **Повторная верификация (stale-gate, 9/9 PASS):** HEAD `7873511` ==
  чистое дерево; живая страница `?v=5`: aria-labelledby в DOM,
  фокус возвращается на `btn-new` после закрытия, regression зелёный.

## Ошибка 13 (аудит, П4). A11y-пробелы: безымянные элементы для скринридеров

- **Симптом (найден независимым ревьюером, 5 находок Medium):**
  1) поиск подписан только placeholder'ом — скринридер объявляет
     безымянное поле;
  2) кнопки «Изменить»/«Удалить» на карточках не говорят, к какому
     проекту относятся (десяток одинаковых «Изменить» в списке);
  3) прогресс-бар — просто div, скринридер не знает ни роль, ни значение;
  4) ошибка валидации `#err-name` визуально рядом с полем, но не связана
     с ним программно (`aria-describedby`), `aria-invalid` не ставился;
  5) `<output>` прогресса обновлялся без `aria-live` — изменение
     не озвучивалось.
- **Исправление (П4):**
  - `aria-label="Поиск по названию и описанию"` на поле поиска;
  - карточка: `aria-labelledby` → `id="title-<uid>"` заголовка;
  - кнопки карточек: `aria-label="Изменить/Удалить проект «Имя»"`
    (имя — через `escapeHtml`, т.к. подставляется в атрибут);
  - дорожка прогресса: `role="progressbar"` + `aria-valuemin/max/now`;
  - `#f-name`: `aria-describedby="err-name"`, `aria-invalid="true"`
    при ошибке (снятие — при вводе и при открытии модалки);
  - `<output>`: `aria-live="polite"`.
- **Верификация (ad-hoc, 21/21 PASS):** STATIC (все атрибуты в
  исходниках, ?v=6) + LIVE: aria-label поиска; `aria-labelledby`
  карточки совпадает с `id` заголовка (`title-<uid>`); aria-label кнопок
  содержат имя проекта; progressbar `aria-valuenow=65` (первая карточка);
  `aria-describedby=err-name`; `aria-invalid` ставится при пустом имени и
  снимается при вводе; output обновился на 80% и имеет `aria-live`;
  regression: 10 карточек, нет баннера, фокус-механика П3 жива.
- **Замечание о тесте (не о коде):** первый прогон дал 20/21 — FAIL был
  дефектом самого теста: программный `.click()` без предшествующего
  `.focus()` не перемещает фокус, поэтому `lastFocused` оставался body.
  WCAG 2.4.3 — критерий для клавиатурных пользователей (фокус всегда на
  триггере до активации); тест исправлен на клавиатурный сценарий.

## Ошибка 14 (аудит, П5). saveProjects без защиты — тихая потеря данных

- **Симптом (найден аудитом):** `loadProjects()` обёрнут в try/catch,
  а `saveProjects()` — нет. При `QuotaExceededError` (переполненное
  хранилище) сабмит менял память, закрывал модалку, показывал тост
  «создан» — но в LS ничего не записывалось. После перезагрузки страницы
  проект исчезал бы бесследно: пользователь до последнего не знал,
  что данные не сохранены.
- **Исправление (П5):**
  - `saveProjects()` обёрнут в try/catch: при ошибке — тост
    «Не удалось сохранить: хранилище недоступно/переполнено» и `false`;
  - все 4 вызывающих места (создание, редактирование, удаление, сброс
    демо-данных) проверяют результат и **откатывают `projects = prev`**
    при неудаче;
  - при неудачном создании/редактировании модалка остаётся открытой —
    ввод не теряется, пользователь может повторить.
- **Верификация (ad-hoc, 15/15 PASS):** STATIC (try/catch, true/false,
  4 проверки результата, 4 отката, ?v=7) + LIVE с подменой
  `Storage.prototype.setItem` на бросающий `QuotaExceededError`:
  нормальное создание (11/LS=11); при отказе — модалка открыта, имя
  в поле, тост об ошибке, в LS проекта НЕТ, баннера нет; повторный
  сабмит после снятия отказа — сохранён (12/LS=12); отказ удаления —
  карточка жива, LS прежний; отказ сброса — счётчик прежний; уборка —
  10 демо-карточек.
- **Замечание о тестах (не о коде):** два прогона вылились в ложные FAIL
  из-за самих тестов: (1) опечатка `orig.call(localStorage,'x')` с одним
  аргументом бросала TypeError и оставляла `setItem` подменённым;
  (2) клик по кнопке ЗА открытой модалкой (dialog делает фон inert —
  реальный пользователь так не может) вызывал `showModal()` на открытой
  модалке → InvalidStateError → красный баннер; (3) LS общий на origin —
  тестовый проект из прошлого прогона становился «дубликатом» и валил
  нормальное создание. Все три — методологические уроки CDP-тестирования,
  зафиксированы здесь.
